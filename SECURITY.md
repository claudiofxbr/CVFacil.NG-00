# Segurança — CVFacil.NG

Registro vivo de achados de auditoria, correções aplicadas e pendências. Atualizado conforme o trabalho avança — não é um documento estático de arquitetura (para isso, ver `SEGURANCA_AUTENTICACAO.md`, mas atenção: aquele arquivo já estava desatualizado antes desta sessão, e agora está ainda mais — a sessão vive num cookie `httpOnly`, não mais em `localStorage`).

## Corrigido

| Item | Data | O que foi feito | Evidência |
|---|---|---|---|
| SSH root com senha | 2026-07-12 | `PermitRootLogin prohibit-password` + `PasswordAuthentication no` no `sshd_config` da VPS de produção | Testado: nova conexão por chave funciona; tentativa por senha rejeitada (`Permission denied (publickey)`) |
| Portas do Docker Swarm expostas (2377, 7946) | 2026-07-12 | Bloqueadas via `ufw deny` | Testado: portas inacessíveis de fora; cluster Swarm continua saudável (`docker node ls` → Ready/Leader) |
| Ausência de headers de segurança HTTP (CSP, HSTS, X-Frame-Options, X-Content-Type-Options) | 2026-07-12 | Adicionados via `headers()` em `next.config.mjs` | Testado com build de produção real: headers presentes, zero violações de CSP no navegador, login funcionando |
| JWT armazenado em `localStorage`, sem `httpOnly` | 2026-07-12 | Migrado para cookie `httpOnly` + `SameSite=Strict`, setado pelo servidor (`login`/`register`), limpo por nova rota `/api/auth/logout`. `localStorage`/`document.cookie` removidos de todos os pontos do cliente. | Testado: `Set-Cookie` com `HttpOnly` confirmado via `curl -i`; resposta JSON não contém mais `token`; sessão sobrevive a refresh; logout limpa a sessão no servidor |
| Dependências vulneráveis sem monitoramento (Dependabot desabilitado) | 2026-07-12 | `gh api -X PUT .../vulnerability-alerts` + `.../automated-security-fixes` | Confirmado via `204 No Content`; alertas reais já visíveis em `gh api .../dependabot/alerts` |
| 4 vulnerabilidades *high* em dependências (Next.js middleware bypass, nodemailer SSRF, ws DoS, protobufjs DoS) | 2026-07-12 | `nodemailer` removido (dependência direta, confirmadamente código morto — nunca referenciado). Next.js atualizado de 16.2.5 (vulnerável) para 16.2.10 (corrigido), o que também atualizou `ws`/`protobufjs` transitivos. | `npm audit`: 8 vulnerabilidades (4 high) → 2 (0 high, só moderate). Build de produção + login/registro/sessão testados após a atualização |
| Sem branch protection em `main` no GitHub | 2026-07-12 | Protecão leve: bloqueia force-push e deleção da branch. **Não** exige PR/review — o fluxo atual é sempre push direto, e exigir review travaria isso por completo (GitHub não permite autoaprovar a própria PR) | Confirmado via `gh api .../branches/main/protection`: `allow_force_pushes: false`, `allow_deletions: false` |
| Container roda como root | 2026-07-12 | `USER node` no Dockerfile (imagem `node:20-slim` já inclui esse usuário, uid 1000), com `COPY --chown=node:node` nos arquivos copiados | Testado com build real: `docker exec ... id` confirma `uid=1000(node)`; registro/login/sessão funcionando normalmente como não-root (inclui o engine binário do Prisma, que precisa de permissão de execução) |
| `/api/crash-report` público sem rate limit | 2026-07-12 | Rate limit por IP (30 requisições / 10 min, mesmo padrão de `lib/rateLimit.ts` já usado em login/register) | Testado com Redis real: 30 requisições seguidas → `200`, próximas 5 → `429`, exatamente no limite configurado |
| `ADMIN_SEED_EMAIL` permanente em produção | 2026-07-12 | Confirmado no banco que a conta admin de bootstrap já existe e está ativa; variável removida do ambiente local e do ambiente da VPS | **Também revelou** que o container em produção estava rodando uma imagem Docker **desatualizada** (recriado sem `docker pull` antes numa correção anterior) — todas as correções de segurança das rodadas anteriores desta sessão só entraram em vigor de fato agora, ao puxar a imagem mais recente do GHCR e recriar o container |
| Porta 3000 (painel EasyPanel) exposta publicamente | 2026-07-12 | **Causa raiz do incidente anterior identificada**: a regra de firewall anterior mirava no endereço interno errado do serviço, por isso nunca interceptava o tráfego de fato (e o efeito colateral observado antes não se repetiu ao corrigir o alvo). Corrigido usando o endereço de destino real, confirmado por inspeção direta de contadores de tráfego. `cvfacil-ng` usa um endereço de container diferente, não é afetado pela regra. | Bloqueio automatizado (script + serviço systemd, sobrevive a reboot). Acesso ao painel agora só via túnel SSH — detalhes de acesso documentados fora deste repositório público. Testado: bloqueio estável em múltiplas rodadas, `cvfacil-ng` nunca afetado |
| Sem backup automatizado do banco (script antigo no repo era de outro projeto/MySQL, não relacionado) | 2026-07-12 | Novo script de backup específico para o Postgres do CVFacil.NG, via `pg_dump` (versão casada com a do servidor, rodando em container Docker para evitar incompatibilidade de versão). Agendado diariamente na VPS, com rotação automática (retém 14 dias). | Testado de ponta a ponta: dump real gerado (96K), validado com `pg_restore --list` — 119 entradas, versão do servidor conferida, tabelas reais da aplicação presentes (não um arquivo vazio) |
| Deploy sem TLS (HTTP puro) | 2026-07-13 | App agora servido via HTTPS real, com certificado Let's Encrypt emitido via desafio DNS-01 (não depende da porta 80, que já pertence a outro serviço nesta VPS; renovação automática). `COOKIE_SECURE` ativado em produção — o cookie de sessão agora exige HTTPS. A URL pública oficial de produção é `https://xavierbr-vps.tech` (domínio confirmado pelo usuário; `cvfacil.ng`, usado em nomes de imagem/e-mails de contato ao longo do projeto, não é o domínio real em uso). Contato de ACME do Let's Encrypt também corrigido para um e-mail real (estava configurado para um endereço em `cvfacil.ng`, que não recebe nada). | Testado de ponta a ponta: certificado válido emitido e confirmado via requisição HTTPS real; fluxo completo de cadastro/login testado sobre HTTPS — cookie de sessão chega com `Secure` + `HttpOnly` + `SameSite=Strict`, e a sessão persiste (`/api/auth/me` → 200); HTTPS confirmado novamente após a correção do e-mail de contato |
| Rate limit de login/registro/crash-report silenciosamente inativo em produção | 2026-07-13 | **Achado em auditoria de saúde do app**: `REDIS_HOST=localhost` no `.env` de produção era resíduo da configuração de desenvolvimento local — não existia nenhum Redis rodando na VPS (nem container, nem no host). Como `lib/rateLimit.ts` é desenhado para falhar aberto (permitir a requisição) quando o Redis está indisponível, o limite de tentativas nunca funcionou de fato em produção, sem gerar nenhum erro visível. Implantado um container Redis dedicado (imagem oficial, sem exposição externa, acessível só internamente via rede Docker isolada) e reapontado o app para ele. | Testado: erros de conexão (`ECONNREFUSED`) sumiram dos logs; 32 requisições seguidas a um endpoint público confirmaram o limite reagindo de verdade (`429` a partir da requisição 31) |
| `/api/crash-report` retornava 500 em vez de tratar entrada inválida | 2026-07-13 | **Achado no mesmo diagnóstico**: o campo `timestamp` do payload não era validado antes de `new Date(...).toISOString()`, e um valor ausente/inválido derrubava a rota com `RangeError`. Não afeta o app real (o cliente sempre envia `Date.now()`), mas a rota é pública e sem autenticação — qualquer requisição malformada direta gerava 500. Corrigido com um fallback seguro. | Testado em build de produção real (`node server.js`, igual ao `Dockerfile`): requisição sem `timestamp` agora responde `200` |
| Logger do servidor mudo em produção | 2026-07-13 | **Achado durante a investigação acima**: `lib/logger.ts` só escrevia no console quando `NODE_ENV === 'development'` — ou seja, todo `logger.error()`/`logger.warn()` do lado servidor era descartado silenciosamente em produção, sem aparecer em `docker logs` nem em lugar nenhum. Isso escondeu a causa real do bug do item acima até uma investigação local. Corrigido: agora sempre loga no servidor (não afeta o console do navegador do usuário final, que continua só em dev). | Testado em build de produção real: log de erro estruturado aparece corretamente em `docker logs` após a correção |
| Usuários novos com 0 créditos não conseguiam salvar o primeiro currículo | 2026-07-28 | **Bug relatado pelo usuário** ("salvar não funciona"): toda conta nova tinha `credits = 0` por padrão, e criar currículo exige crédito > 0 — o primeiro salvamento de qualquer usuário sempre falhava com 403. Corrigido concedendo 3 créditos grátis no cadastro. Corrigido também: o clique em "Salvar" sempre tentava abrir uma janela de impressão de PDF que navegadores costumam bloquear (o `window.open` roda depois de um `await`, perdendo a permissão de gesto do usuário); quando bloqueado, o usuário era levado de volta ao dashboard sem nunca ver que o salvamento (esse sim) tinha funcionado. | Testado contra o Neon real e via navegador: cadastro concede 3 créditos, criação do primeiro currículo funciona, confirmação de sucesso aparece antes de qualquer tentativa de PDF |
| Bug financeiro crítico: webhook do Stripe sobrescrevia créditos em vez de somar | 2026-07-28 | **Achado em auditoria técnica de 22/07** (`AUDITORIA_TECNICA_2026-07-22.md`, item C1): um usuário com créditos restantes que comprava outro plano tinha o saldo **resetado**, perdendo créditos já pagos, silenciosamente. Corrigido para somar (mesmo padrão já usado na concessão manual de créditos por admin). Somar exigiu também uma guarda de idempotência nova (Stripe reenvia o mesmo evento de webhook em retries) — implementada via `INSERT...ON CONFLICT...RETURNING (xmax = 0)`, que só credita na primeira entrega de cada evento. | Testado contra o Neon real: duas entregas simuladas do mesmo evento — a primeira credita, a segunda é corretamente ignorada; saldo final é a soma exata esperada |
| Corrida de concorrência na criação de currículo podia deixar créditos negativos | 2026-07-28 | Achado A1 da auditoria: saldo lido, validado em JS e decrementado numa transação separada sem guarda — duas requisições concorrentes com saldo=1 podiam ambas passar. Corrigido com débito atômico via CTE SQL (`UPDATE ... WHERE credits > 0`, insert só se o débito afetou uma linha). | Revisão de código + build de produção testado |
| Circuit breaker do Gemini admitia múltiplos testes de recuperação simultâneos | 2026-07-28 | Achado A2: a transição OPEN→HALF_OPEN não era atômica, inundando a API na recuperação em vez de testá-la com cautela. Usado de verdade por `/api/suggestions` (confirmado antes de corrigir). Corrigido com flag de trial único em voo. | Revisão de código + build testado |
| `import-resume` aceitava qualquer arquivo sem validar tipo/tamanho antes de gastar cota da Gemini | 2026-07-28 | Achado A6: validação de PDF/50MB existia em código morto, nunca chamada pela rota real. Adicionada validação direto na rota. | Build testado |
| `GET /api/crash-report` sem autenticação | 2026-07-28 | Achado A9: comentário no próprio código dizia "adicionar depois". Hoje inofensivo (leitura do banco comentada), mas ficava pronto pra vazar dados se reativado sem lembrar do auth. Corrigido com checagem de admin + rate limit. | Build testado |
| Pipeline morta de fila do Gemini (BullMQ/worker) — código e 5 tabelas sem uso real | 2026-07-28 | Achado A5: `QueueManager.enqueuePDF` nunca era chamado por nenhuma rota; a rota real (`import-resume`) chama a Gemini de forma síncrona. Removido: 6 arquivos em `lib/gemini/`, `scripts/start-worker.ts`, dependência `bullmq`, e os 5 modelos Prisma correspondentes (confirmadas vazias — exceto a linha singleton padrão de uma delas — antes do `DROP TABLE`). | Migration aplicada contra o Neon de produção; build e suíte de testes completa (52 testes) passando depois |

Substituída por 16 testes reais cobrindo hashing de senha, JWT, extração de token e opções do cookie de sessão. O runner do Jest (quebrado por uma dependência corrompida) também voltou a funcionar, de brinde, numa reinstalação limpa. | 52/52 testes passando |
